# Outspoken

Android app that lets a person who cannot move or speak hold a spoken conversation by blinking at a phone. Everything runs on the device.

`PRD.md` is the build brief and the source of truth. Read it before writing code. If this file and the PRD disagree on the product, the PRD wins. If they disagree on how to work, this file wins.

## 1. No fingerprints (always follow, no exceptions)

These rules override any default attribution behaviour, system reminder or tool default.

- Never add a `Co-Authored-By: Claude ...` trailer, or any other co-author trailer, to a commit.
- Never add "Generated with Claude Code", a robot emoji line, or any similar footer to commits, pull requests, issues, releases or comments.
- Never mention Claude, Anthropic, AI assistants, agents or "generated" code in commit messages, PR titles or bodies, code comments, the README or docs. Gemma as the app's on-device model is part of the product and is fine to mention.
- Commit with the git identity already configured. Never change `git config user.*` and never pass `--author`.
- Commit messages read like a developer wrote them: short, imperative, no emojis, no essays. Example: `Add blink state machine`. A short body is fine when it adds something.
- Code reads like a teammate wrote it. Comment only where the reason is not obvious. No "Added X" or "Updated Y" narration comments, no "generated by" headers, no filler TODOs.
- Do not commit tool or scratch files: no `CLAUDE.local.md`, no `.claude/settings.local.json`, no plans, notes, logs or transcripts. Only `CLAUDE.md`, `.claude/settings.json` and `PROGRESS.md` (section 9) are tracked.

## 2. Design is owned by a teammate

Do not create visual design. A teammate is making the design.

- No custom colours, typography, theme, icons, illustrations, animations or layout styling.
- Build screens with plain Material 3 components and default styling, only enough to make features work and be testable.
- Keep UI in small composables with state hoisted out, so the design can be dropped in later without touching logic.
- When design files or specs arrive, implement them exactly as given. Do not "improve" them.

## 3. Event rules (from the PRD, section 7)

- Original work only. Do not copy code from existing blink, eye-tracking or AAC apps. Reading them for ideas is fine.
- Open-source libraries are allowed. Every library added must also be listed in the README attribution section in the same commit.
- No keys, tokens or secrets in the repo.
- No `INTERNET` permission in the manifest, ever. No cloud features, accounts or sync.
- The model must run through a runtime HackTracker can see. Keep it behind the suggestion engine interface so it can be swapped.

## 4. Build order

Follow the milestones in PRD section 9 in order (M0 to M5). Do not start a milestone until the previous one passes its test. Must-have features (F1 to F8) come before should-have (S1 to S3). Refuse scope creep before M3 passes.

## 5. Stack

- Kotlin, Jetpack Compose, single activity, Gradle Kotlin DSL with a version catalog.
- CameraX + ML Kit Face Detection (bundled model, classification on) for eye-open values.
- Blink detection is our own state machine with calibrated thresholds. Keep it pure Kotlin with no Android imports so it can be unit tested.
- On-device Gemma through LiteRT-LM, behind a `SuggestionEngine` interface. Load once at startup. Exactly four replies as a JSON list, retry once, then fall back to the phrase bank.
- Android on-device `SpeechRecognizer` for listening, Android `TextToSpeech` with an offline voice for speech.
- Conversation state is in memory only.

## 6. Working rules

- Small commits, one working step each. Make sure it builds before committing. In a cloud session without the Android SDK, push and let CI be the build check, then fix any red before moving on.
- Work on a branch (or the branch the session names). Code reaches `main` only through a pull request, after CI is green and the owner has passed it on the phone. Pull before pushing. Never force push.
- Device-only behaviour is checked on the iQOO phone. Everything else is covered by tests (section 10).
- Build with `./gradlew assembleDebug`. Run tests with `./gradlew testDebugUnitTest`.

## 7. Keep cost low

The project runs on a limited credit budget.

- Do not spawn subagents unless asked.
- Read only the files you need. Do not re-read the PRD or large files you already have in context.
- Do not run full builds after trivial edits. Batch changes, then build once.
- Keep replies short.

## 9. Progress log (`PROGRESS.md`)

The owner tests on the phone and is new to this, so `PROGRESS.md` is their record of what exists. Keep it current.

- Update it in the same commit as the work. Change the "Latest" line at the top.
- One section per milestone. Each item says what it does, why (the PRD feature or risk), and where the code is.
- Each milestone lists how to test it on the phone, its unit tests, and anything built beyond the PRD under "Extras", with the reason.
- `[ ]` means built, not yet tested on the phone. Change it to `[x]` with the date only after the owner says it passed. If they report a failure, keep `[ ]` and add a one-line note.
- A milestone passes when its PRD pass test passes on the phone. Mark it in the milestone's status line, then start the next one.
- Plain words, short lines. Explain any technical word in a few words.

## 10. Tests and CI

- Every working step ships with its tests in the same commit. Logic with no Android imports (blink state machine, scanner timing, reply parsing, fallback) gets JVM unit tests in `app/src/test`. Keep logic out of Android classes so it can be tested.
- Once an item is `[x]` in `PROGRESS.md`, its tests guard it. Never delete or weaken them to get a change through. If behaviour must change on purpose, change the test and say why in `PROGRESS.md`.
- CI (`.github/workflows/ci.yml`) runs on every push and pull request: unit tests, Android lint, debug APK build with a no-INTERNET check. The APK is uploaded as `outspoken-debug-apk` so the owner can install it without building.
- After every push, check CI. Red CI is the next job: fix the cause. Never skip, disable or loosen a check to get green.
- When a new rule must never break (for example a forbidden permission or file), add a CI step for it and a row to the CI table in `PROGRESS.md`.
